The idea

  

    

      
A README tells you what a project does. It rarely shows why it is built that way, and it drifts away from the code over time.

      
    
        
  • Why first, code last. Each deck starts with the problem, then the architecture, then one slide per component, with short real code excerpts.
    • 
        
  • Demos run the real logic. Simulations port the project's own functions (thresholds, ordering, integer maths), so playing with them teaches how the code behaves.
    • 
        
  • The code wins. Every number on a slide comes from the source. Where the docs say something else, the skill reports it instead of hiding it.
    • 
        
  • Nothing to install. Plain HTML, CSS and JS, no CDN, no build. It works offline and on any static host.
    •

The code is the source of truth

  

    

      
Step 2 of the skill: get every timeout, threshold, default and endpoint from the code, not the README. Keep a list of the places where they disagree.

      
    
        
  • Why: an explainer that repeats a stale README spreads the mistake to more readers, who now trust it more because it looks polished.
    • 
        
  • Never fix quietly. The slides show what the code actually does, and the list goes to the maintainer, who decides whether the code or the docs is wrong.
    • 
        
  • Dead ends count too: a CI job whose consumer doesn't exist, a flag nothing reads.
    • 
      

    

    

      
Found while building this deck

      
    
        
  • SKILL.md's template table listed five files, but templates/ also held app.js, the starter for the project's demos.
    • 
        
  • The Pages template pinned actions/checkout@v4.2.2 (Node 20), while this repo's own ci.yml had already moved to Node 24 actions.
    • 
        
  • ci.yml's comment said the zip goes under Settings → Skills; the release notes it writes said Settings → Capabilities → Skills.
    • 
        
  • Testing at phone width turned up a template bug: wide code blocks pushed grid columns past the screen edge.
    • 
      

      
All four were reported to the maintainer first, then fixed in the skill's 1.1.0 release.

    

  






  
A simulation that only looks right is a bug

  

    

      
Demos port the project's own function and name it on the slide, so the reader can go and find it.

      
    
        
  • Same maths. Integer division stays integer, thresholds keep their exact values, branches keep their order.
    • 
        
  • Same edge cases. If the firmware ignores a button press during boot, the simulation does too.
    • 
        
  • In this deck: the version-check demo is a line-for-line port of scripts/check-versions.py, and the tag parser reproduces the shell expansions in ci.yml.

The engine: deck.js

  

    

      
125 lines, no dependencies, shared by every generated site. Project code never edits it; it calls the small window.Deck API from app.js.

      
    
        
  • One URL per slide. #/slide-id via history.replaceState, so links to a slide work and Back leaves the deck instead of stepping through it.
    • 
        
  • Keyboard and touch. Arrows, Space, PageUp/Down, Home/End, O overview, Esc. Inputs keep their own arrow keys; swipes starting on a control are ignored.
    • 
        
  • Animate only what is visible. One requestAnimationFrame loop calls only the hooks of the active slide.
    •

One accent, no external requests

  

    

      
deck.css defines the colours as CSS variables. A project re-tints the whole deck by changing --accent.

      
    
        
  • Dark by default. Diagrams are inline SVG drawn with the same tokens, so they re-tint too.
    • 
        
  • No CDNs, no web fonts. System font stacks only. The site loads behind a corporate proxy, on a locked-down Pages host, or from a laptop with no network.
    • 
        
  • Phone-friendly. Below 860 px the columns stack; below 480 px the grids go single-column.

Photos carry where they were taken

  

    

      
Phone photos usually contain GPS coordinates in their EXIF data. Once pushed, they are in git history for good.

      
    
        
  • Copies are cleaned. Images go to site/img/ resized and with metadata removed.
    • 
        
  • Originals are checked. The skill looks for GPS tags in the repo's own images and warns you if it finds any.
    • 
        
  • Your call. Removing a file from history needs a history rewrite and a force-push, so the skill only reports it.
    •

Publishing: static files, no build

  

    

      
The workflow uploads site/ as it is. It runs when site/** or the workflow changes on main.

      
    
        
  • GitHub: enable Pages once with source = GitHub Actions. It only deploys from the default branch.
    • 
        
  • GitLab: a pages job is merged into the existing .gitlab-ci.yml, never overwriting it. Pages turns on by itself.
    • 
        
  • README link. A short paragraph points readers to the deck.
    • 
      


# one-time, GitHub
gh api -X POST repos/OWNER/REPO/pages -f build_type=workflow

    

    

      
.github/workflows/pages.yml


on:
  push:
    branches: [main]
    paths: ["site/**", ".github/workflows/pages.yml"]
permissions:
  pages: write
  id-token: write
steps:
  - uses: actions/checkout@v7.0.1
  - uses: actions/configure-pages@v6.0.0
  - uses: actions/upload-pages-artifact@v5.0.0
    with: { path: site }
  - uses: actions/deploy-pages@v5.0.1

    

  







  
From release.sh to a GitHub Release

  

    
    

      
    
        
  1. release.sh P X.Y.Z refuses unless the version is X.Y.Z, the plugin exists, you're on main with a clean tree; then git pull --ff-only.
    2. 
        
  2. Writes the version into plugin.json and the plugin's marketplace.json entry.
    3. 
        
  3. Runs check-versions.py P X.Y.Z and claude plugin validate locally.
    4. 
        
  4. Commits release: P vX.Y.Z and pushes main.
    5. 
        
  5. claude plugin tag creates and pushes the P--vX.Y.Z tag.
    6. 
        
  6. The tag push starts CI: install Claude Code 2.1.302, validate every manifest, check versions, check the tag.
    7. 
        
  7. release job (needs validate): zip P/skills/P, write notes from commits touching P/ since its previous tag.
    8. 
        
  8. gh release create --verify-tag. Users update through the marketplace, or upload the zip to claude.ai.
    9. 
      

      

    

  






  
How CI reads a tag

  
The workflow triggers on tags matching *--v*, then splits them with two shell expansions. Type a tag.

  

    

      
      

        
        
        
        
        
      


# .github/workflows/ci.yml
TAG="${GITHUB_REF#refs/tags/}"
python3 scripts/check-versions.py "${TAG%--v*}" "${TAG##*--v}"

Two ways to install

  

    

      
Claude Code: the marketplace

      
The repo itself is the marketplace. Claude Code reads .claude-plugin/marketplace.json from GitHub and installs plugins from the folders it lists.


/plugin marketplace add mveplus/claude-skills


/plugin install how-it-works-site@mveplus-skills

      
Update later with /plugin marketplace update mveplus-skills.

    

    

      
claude.ai: the release zip

      
The release job zips only the skill folder, so the archive has how-it-works-site/SKILL.md at its root, the shape claude.ai expects.


# ci.yml, release job
(cd "$PLUGIN/skills" && zip -qr \
  "$GITHUB_WORKSPACE/$PLUGIN-$VERSION.zip" "$PLUGIN")

      
Upload it under Settings → Capabilities → Skills.

    

  







  
The ideas behind it

  

    
Code over docs
Facts come from the source; mismatches are reported, not smoothed over.

    
Real simulations
Demos port the project's functions and name them on the slide.

    
Zero dependencies
Static files, system fonts, inline SVG. Works offline and anywhere.

    
Ask, then act
Questions before building; confirmation before committing or pushing.

    
Generic engine
deck.js never changes per project; app.js holds the specifics.

    
Privacy by default
Images stripped of metadata; GPS in originals is flagged.

    
One version, two files
release.sh writes both; CI refuses to ship if they drift.

    
Tag = release
Pushing P--vX.Y.Z is the only way a release gets published.
